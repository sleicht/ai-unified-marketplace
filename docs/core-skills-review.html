R4 · Fix · Cross-skill compatibility

Reverse engineering needs the same requirements contract.

Current mismatch

The filename matches; the structure does not.

The reverse-engineering reference permits a prose-only Functional Requirements section: recovered behaviour is delegated to use-case specs.

The forward skill requires FR tables with IDs, user stories, priorities and statuses. The diagram skill requires each UC to trace to an FR.

A new reverse-engineered catalogue can therefore leave nothing concrete for that traceability check to resolve.

Recommended change

Recover evidence-backed FR rows.

  • Reuse the forward table structure and stable headings, including Requirements Notes.
  • Give each recovered FR an ID and link each UC to its FRs; the UC format already permits a Requirements field.
  • Record source paths and uncertainty. Do not infer business priority, approval or unevidenced NFRs from code alone.
  • Keep unknowns explicit instead of filling gaps with invented requirements.
Acceptance: run the forward diagram/specification checks on recovered documents without first repairing their catalogue structure.

R5 · Tighten · Update behaviour

Preserve identity when the specification changes.

Several skills say “create or update”, but do not explicitly reconcile existing IDs, content and downstream references before writing.

Illustrative failure

A new goal changes the order.

An existing UC-004 can be reassigned during regrouping by actor or importance. A renamed diagram label can produce a new filename while TC links still point to the old one.

The business-rule contract adds a real constraint: rules are numbered without gaps, and the bundled Studio format says they are positional.

Recommended update contract
  1. Read existing output first; match by ID and business meaning.
  2. Keep existing FR, UC and TC IDs. Allocate new IDs without renumbering other items.
  3. Preserve unaffected content; report removed or renamed items and affected links.
  4. When BR renumbering is required, produce an old → new mapping and repair authorised references; report consumers outside the task scope.
Acceptance: adding a UC, renaming a UC and deleting a business rule leave unrelated IDs intact and all affected references resolved or explicitly reported.

R7 · Fix · Path and task scope

Resolve the skill and the project independently.

The use-case and reverse-engineering skills mix an installed-skill-relative script path with a project-relative document path in one command.

Current instruction pattern
python3 scripts/validate_use_case.py \
  --strict docs/use_cases/UC-*.md

Running from the project usually misses the bundled script. Running from the skill directory usually misses the project docs. The wildcard also selects unrelated UCs.

Recommended behaviour
  • Resolve the installed script to an absolute path.
  • Resolve the selected project/service docs separately.
  • Pass an explicit, quoted list of files created or updated by this task.
  • End with the output path, checks and unresolved dependencies, so the next chat can work from files.
Acceptance: the same single-UC request works from project root and service directory, with the skill installed elsewhere. An unrelated invalid UC is left untouched.

R8 · Tighten · Lifecycle and uncertainty

Keep the same meaning across languages and revisions.

Confirmed inconsistency

English and German states diverge.

English defines Deferred and Rejected. German defines Abgelehnt and Ersetzt, but no equivalent of Deferred.

The lists are not a one-to-one vocabulary: postponement, rejection and replacement describe different outcomes.

Change: define an explicit mapping, add a German deferred state, and support superseded consistently only if it is needed.

Recommended safeguards

Distinguish proposals from agreed facts.

  • When making an NFR measurable, label the threshold as proposed until confirmed; keep that uncertainty in Requirements Notes.
  • Separate a requirement’s delivery state from review/conflict notes instead of adding ad-hoc status values.
  • For test cases and UC templates, clarify “Reviewed”: its current definition says it is still awaiting stakeholder review.
Acceptance: a deferred requirement retains its meaning when translated. An unanswered performance question cannot silently become an approved limit.
