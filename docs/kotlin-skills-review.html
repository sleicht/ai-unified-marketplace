  • Vertical feature slices and private persistence mappers.
  • Domain repository ports; route-local response mapping.
  • Feature-owned Koin modules and full composition-root verification.
  • Services only where orchestration warrants one.

UI boundaries

  • Transport ports and constructor injection.
  • Immutable state plus action contracts for meaningful screen sections.

F2 · Addressed · Original finding below

A nullable column feeds a non-null invariant.

Implemented: Required reference/category/name fields agree across domain, SQL and Exposed. All persisted fields and OffsetDateTime audit values are mapped; database constraints and round trips are tested. Current source →

Original example
val externalReference: String? = null

init {
    require(!externalReference.isNullOrBlank())
}

// RecordTable
varchar("external_reference", 50).nullable()

A default construction fails validation. A database row allowed by the table mapping can fail during hydration. Audit timestamps are also silently left at their null defaults by the mapper.

Proposed contract
// If the domain requires a reference:
val externalReference: String

init {
    require(externalReference.isNotBlank())
}

// Corresponding Exposed column:
varchar("external_reference", 50)

Use matching SQL NOT NULL and the agreed blank/length rules. Map all persisted fields, including audit timestamps, with explicit timestamp imports/conversions.

Alternative: if the real domain allows a missing reference, keep nullability and validate only present values. Establish the domain rule first; existing nullable rows need a migration plan before tightening constraints.

Verify: persist and reload every field; exercise null/blank boundaries and any historical rows affected by a constraint change.

Evidence: implement:102–117,134–139,163–168. The mismatch is confirmed in the examples; actual database contents were not inspected.

F3 · Addressed · Original finding below

Cancellation should leave quietly.

Implemented: The ViewModel rethrows CancellationException and uses a stable failure message. Cancelling its screen scope produces no visible error. Current source →

Original catch block
} catch (e: Exception) {
    searchState = searchState.copy(
        error = "Failed to load records: ${e.message}"
    )
}

Coroutine cancellation is caught as a loading failure. The snippet also puts arbitrary exception text directly into visible UI.

Replacement fragment
import kotlin.coroutines.cancellation.CancellationException

// After the successful load:
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    searchState = searchState.copy(
        error = "Could not load records. Try again."
    )
}

Preserve cancellation. Prefer the project's typed error mapping; keep diagnostic details in its existing reporting mechanism.

Verify: suspend the fake port, cancel the load and assert no failure message is produced. Separately throw a transport error and assert the stable user-facing message.

Evidence: implement-ui:154–168. Behaviour supported by Kotlin coroutine exception handling. The concurrency policy on the next slide must also govern state updates in finally.

F4 · Addressed · Original finding below

Two clicks can race. Search ignores its query.

Implemented: Search propagates its submitted query. Cancelling previous work and checking request identity protects current results, errors and loading state; controlled-completion tests cover both completion orders. Current source →

Observed
  • Every loadRecords() launches another coroutine.
  • Either completion sets isLoading = false, even while another load remains active.
  • An older response can overwrite a newer response.
  • onQueryChange stores text, but listRecords(limit = 100) neither receives nor filters by that text.
Smallest coherent example

Teach a list refresh if that is the intended use case: remove the illustrative search field/action and ignore repeat refreshes while a load is active.

If search is intended, pass the query through the real contract and implement latest-request-wins behaviour. Cancel or invalidate prior work, and prevent stale completion/finalisation from changing current state.

Choose by behaviour: one in-flight load is simpler for refresh. Latest-request-wins is appropriate for changing search inputs. A disabled button alone does not define the ViewModel's concurrency contract.

Verify: use controllable fake responses, start A then B and complete them in reverse order. Assert the chosen result and loading state. For search, assert the submitted query reaches filtering or the port.

F5 · Addressed · Original finding below

Decoding JSON is not HTTP error handling.

Implemented: Production and MockEngine share expectSuccess configuration. Tests cover 401/403/500 with list-shaped bodies, malformed JSON, encoded queries and auth headers; client ownership and cleanup are explicit. Current source →

Original example

The default client installs JSON negotiation and immediately calls .body(). There is no status validation or explicit response mapping.

Ktor does not reject responses by status by default. A 500 containing [] could therefore look like a successful empty list; an error object could instead surface as a decoding failure.

Concrete correction
internal fun HttpClientConfig<*>.configureServiceClient() {
    expectSuccess = true
    installServiceContentNegotiation()
}

Use this shared configuration for production and MockEngine clients if the project uses exception-based HTTP errors. Otherwise explicitly map statuses into the existing error contract.

Do not impose this choice on a project that deliberately handles non-2xx responses itself.

Verify: return 401, 403 and 500, including a valid list-shaped error body. Assert none becomes successful data. Also test malformed successful JSON.

Related suggestion: make HttpClient ownership explicit and close it at its owner’s lifecycle boundary; close test clients in cleanup. Keep ignoreUnknownKeys when intended; require a concrete interoperability reason for isLenient = true.

Evidence: implement-ui:89–121 · ExampleScreenTest.kt:29–51. Default behaviour: Ktor response validation.

F6 · Addressed · Original finding below

JDBC stays blocking inside a suspend function.

Implemented: JdbcTransactionRunner uses Dispatchers.IO and an explicit transaction contract. The application service owns atomic pair creation; a PostgreSQL test proves the first write rolls back when the second fails. Current source →

Original guidance

The backend guide calls suspendTransaction “coroutine-safe”; the implementation example imports its JDBC variant and supplies no dispatcher or project transaction helper.

The name alone does not establish safe execution on the caller’s thread. Actual blocking risk depends on the target runtime and existing transaction helper.

Replacement instruction

“Determine whether the project uses JDBC or R2DBC. For JDBC, reuse the project's transaction helper and blocking-I/O dispatcher. For R2DBC, use its suspend transaction API. Follow the installed Exposed version.”

“When a use case requires atomic multi-repository work, show one transaction owner and how repository calls participate in that transaction.”

The DI example injects transactionRunner, but no example defines its contract or uses it. Add one small service example that demonstrates the existing project boundary; avoid inventing a transaction framework.

Verify: review the actual dispatcher/helper and execute a two-write rollback test: force the second operation to fail and confirm the first write is absent.

Evidence: implement:149–160,200–210 · backend-style:69. Driver distinction: Exposed transactions. This is a guidance defect, not a measured performance finding.

Kobweb assessment · Skills now available

Yes to a Kobweb skill.
Choose it for the web.

The implemented aiup-kobweb-ui skill is intended for browser applications. Keep the current Compose Multiplatform skill for projects that need its shared desktop/browser UI.

What Kobweb changes

Kobweb builds on Compose HTML and Kotlin/JS: pages render HTML, with browser routing and CSS-based presentation. Silk supplies optional styling and widgets.

This replaces the current Material 3 / Compose Multiplatform rendering approach. It still uses the Compose runtime.

My selection criteria

Prefer Kobweb when browser behaviour, semantic HTML, URLs, CSS and integration with web libraries dominate.

Retain Compose Multiplatform when reusing the same screen implementations across desktop and browser is a central requirement. A Kotlin language match does not make the UI components interchangeable.

Start with one representative browser use case. Measure the resulting accessibility, development effort, payload and interactions. Neither framework guarantees a faster or more accessible application by itself.

Framework facts: What is Kobweb · Silk. Selection criteria are this review’s recommendation. The upstream latest-release link resolved to v0.25.1 during research; use a verified compatible toolchain, not an unqualified “latest”.

Kobweb-specific safeguards

Export is another execution environment.

Static export

Kobweb exports page snapshots through a headless browser. It offers static and full-stack layouts; static export is a natural fit for keeping the existing backend.

Dynamic routes are not automatically enumerated. Add known public routes where needed and configure the host’s fallback behaviour for client-side routes.

Do not describe this as per-request server-side rendering or assume every dynamic page receives pre-rendered HTML.

Authenticated pages

Use an anonymous, deterministic shell during export. Kobweb exposes AppGlobals.isExporting for conditional behaviour.

The skill should prevent login redirects and private API calls during export. At runtime, reuse the real browser auth flow; hiding a page never replaces backend authorisation.

Test callback URLs, expired sessions and the deployed base path.

Verify: export without user credentials; check that no private response data enters generated assets; open a deep link directly in production mode. Ensure frontend fallbacks do not turn API errors into HTML success responses.

Export behaviour and APIs: Kobweb exporting. The fixture verifies an anonymous export and controlled HTTP failures; real authentication remains application-specific. Keep export verification finite and distinguish the development server from the deployed site.
